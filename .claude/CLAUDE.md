# Agent Framework

This is an **execution framework** for Claude Code. The human handles planning and
requirements through conversation; this framework handles turning finalized
requirements into working, tested, committed code.

There are two phases:

- **Design phase** (`/design`) — conversational. Produces planning docs in the
  target product repo. Nothing here writes application code.
- **Implement phase** (`/implement`, `/implement-epic`) — executes finalized
  designs: writes code, writes and runs tests, commits. Nothing here invents
  requirements; it only builds what the design phase already decided.

The implement phase ends in a PR phase: once a feature's last story is
committed, `/implement` (or `/implement-epic`) runs `pr-create` →
`pr-review` → a capped `fix-review` loop, then asks the user to confirm the
merge. Merging always requires an explicit human yes. `pr-create`,
`pr-review`, and `fix-review` also remain independently invocable.

## Directory map (this framework repo)

- `commands/` — one Markdown file per slash command. Some commands
  (`design.md`, `implement.md`, `implement-epic.md`) are orchestrators that
  call the other command files in sequence as steps.
- `agents/` — system prompts for specialist agents spawned by commands via the
  Agent tool.
- `templates/` — Markdown templates used when generating docs/stories.
- `rules/` — standing constraints (`coding-style.md`, `security.md`,
  `testing.md`) that agents must consult before writing or testing code.
- `skills/` — reusable capabilities, added as they come up. Currently only
  `update-agent-framework.md`.
- `scripts/sync-framework.sh` — syncs this framework into the `.claude/`
  directory of the current working directory (the target product repo). Run
  from the product repo whenever the framework changes.
- `scripts/schedule-resume.sh` — schedules a one-shot headless run in a
  product repo after a delay (e.g. `4h`); defaults to
  `claude -p "/implement-epic <feature-id> headless"`. Armed by the
  `/schedule-resume` command, for resuming a specific Epic after a token-limit
  reset.

## Knowledge structure (target product repo, created by deploy + design)

```
my-app/
  knowledge/
    config.json
    state.json
    strategy.md
    requirements/
      LFC-001-user-auth/
        gather.md          ← step 1 output: full Q&A record
        analysis.md        ← step 2 output: codebase findings
        architecture.md    ← step 2 output: approach + data model + API
        stories/
          LFC-STORY-001-001.md
          LFC-STORY-001-002.md
    implementations/
      LFC-001-user-auth/
        implementation-summary.md
        test-results.md
    documentation/
      CHANGELOG.md
      architecture-overview.md
      api-reference.md
      LFC-001-user-auth/
        technical-doc.md
```

`knowledge/` lives inside the product repo being built, not in this framework
repo. `strategy.md` holds project-wide steering decisions from
`/strategize` (business/UX/technical direction), appended to over time and
read by `/design`'s `analyze.md` step for every feature. `requirements/`
holds design-phase output — `gather.md` (the Q&A record), `analysis.md`
(codebase findings), `architecture.md` (technical approach), and
`stories/*.md` (one file per story). There is no `requirements.md` — scope
and business rules live in `gather.md`. `implementations/` holds
implement-phase output, growing per story as `/implement` or
`/implement-epic` runs. `documentation/` holds technical documentation
generated by `/pr-create` — a per-feature `technical-doc.md`, plus
cumulative `CHANGELOG.md`, `api-reference.md`, and `architecture-overview.md`
updated across features.

## State tracking

`knowledge/state.json` is the single source of truth for project-wide
progress, spanning every feature and every story. It is created by the
first `/design` run (alongside `config.json`) and updated by every command
that changes progress — never by hand. Shape:

```json
{
  "schemaVersion": 1,
  "lastUpdated": "2026-07-05T12:00:00Z",
  "features": {
    "LFC-001-user-auth": {
      "design": "complete",
      "branch": "feature/LFC-001-user-auth",
      "stories": {
        "LFC-STORY-001-001": { "status": "committed", "step": null, "commit": "abc1234" },
        "LFC-STORY-001-002": { "status": "in_progress", "step": "test", "commit": null }
      },
      "pr": { "number": 42, "url": "…", "state": "changes_requested", "reviewCycles": 2 },
      "asana": {
        "epicGid": "1234567890",
        "stories": {
          "LFC-STORY-001-001": "1234567891",
          "LFC-STORY-001-002": "1234567892"
        }
      }
    }
  },
  "resume": { "feature": null, "story": null, "note": null }
}
```

- `design`: `in_progress` (set when `/design` creates the feature folder) →
  `complete` (set when `review.md` ends). Story entries are created as
  `pending` when `draft.md` writes each story file. Asana GIDs are recorded
  in the `asana` field after `draft.md` creates the Epic and subtasks.
- Story `status` lifecycle: `pending` → `in_progress` (with `step` set to
  `plan`/`execute`/`test`/`commit` as the story moves) → `tested` →
  `committed`, or `failed` (test failure awaiting a decision) / `skipped`
  (user chose to skip). `commit.md` also ticks the story file's own
  `## Status` checklist so the two never disagree.
- `pr.state`: `none` → `open` → `changes_requested`/`approved` → `merged`.
  `reviewCycles` counts fix-review loops (hard cap 5, see
  `commands/fix-review.md`).
- Write rule for every command: update `state.json` **immediately after**
  the transition it records actually happened (after the commit exists,
  after the PR is open) — never before. A crash must leave state behind
  reality, never ahead of it. `/status` reads this file; `/resume` uses it
  to continue an interrupted run, verifying it against git/disk first.

## Encoding scheme

- `knowledge/config.json` stores the product prefix and counters:
  ```json
  {
    "prefix": "LFC",
    "nextFeatureNumber": 2,
    "nextStoryNumber": { "LFC-001-user-auth": 3 }
  }
  ```
- Created automatically the first time `/design` runs in a project with no
  `config.json` — it will ask for the product name once and derive the
  prefix.
- Feature folders: `<PREFIX>-<NNN>-<slug>` (e.g. `LFC-001-user-auth`).
- Stories: `<PREFIX>-STORY-<feature-NNN>-<story-NNN>` (e.g.
  `LFC-STORY-001-001`), one file per story inside the feature's `stories/`
  dir. The first `NNN` is the feature's own number (so story codes stay
  unique across features); the second `NNN` is a per-feature counter that
  resets to `001` for each new feature.
- Scope and business rules live in `gather.md` (no separate `requirements.md`).
  Story files reference `gather.md` sections rather than numbered requirements.

## Commands

| Command | Phase | Purpose |
|---|---|---|
| `/strategize` | strategy | Standalone, used on a new project and ongoing. Conversation with the `strategist` agent on business/UX/technical direction, recorded to `knowledge/strategy.md` |
| `/product-manager next-task` | strategy | Standalone, sits between `/strategize` and `/design`. Spawns the `product-manager` agent to recommend the next feature to design, based on `knowledge/strategy.md` and what's already designed/implemented. Advisory only — writes nothing |
| `/design` | design | Orchestrates `gather` → `analyze` → `draft` → `review` to produce a finalized-when-you-stop set of docs for one feature |
| `/implement` | implement | Implements a single story: `plan` → `execute` → `test` → `commit`. When the story just committed was the feature's last remaining story, continues into the PR phase: `pr-create` → `pr-review` → `fix-review` loop → merge confirmation |
| `/implement-epic <id>` | implement | Runs `/implement` for every remaining story in one Epic (e.g. `/implement-epic LIB-002`). Resolves the full folder from `state.json`, fetches story order from Asana subtasks, skips already-committed stories, respects `Depends on` ordering, marks Asana subtasks complete on commit, runs the PR phase once at the end |
| `/schedule-resume` | implement | `/schedule-resume <feature-id> <delay>` (e.g. `/schedule-resume LIB-002 4h`) schedules a headless `/implement-epic <feature-id>` run after the delay — for picking up after a token reset. One scheduled run at a time; doesn't survive a reboot |
| `/status` | any | Read-only. Reports project-wide progress from `knowledge/state.json` (design/story/PR state per feature), cross-checked against git and GitHub, and names the next action |
| `/resume` | any | Continues from wherever `state.json` says work stopped — mid-story, next pending story, or the PR phase — for a single stall point. `/resume headless` defines the headless confirmation rules all scheduled runs follow (commits only on clean passes, never merges) |
| `/pr-create` | git | Runs as `/implement`'s PR phase or standalone. Generates technical documentation via `docs-writer`, pushes the feature branch, opens (or updates) the PR with a description generated from `implementation-summary.md`, then runs `/pr-review` against it |
| `/pr-review` | git | Runs inside the PR phase or standalone. Spawns the `reviewer` agent with no conversation context to review a PR diff and submit an actual GitHub PR review (approve/request changes/comment) |
| `/fix-review` | git | Runs inside the PR phase or standalone against a PR with changes requested. Loops fix → re-test → push → re-review, capped at 5 cycles for the PR's lifetime; ends at approval or a surfaced stop. Never merges |

There is no `/finalize` command — whatever is on disk in `knowledge/` when you
stop talking during `/design` is what `/implement` will read.

## Agents

| Agent | Role |
|---|---|
| `strategist` | Helps decide/revise project-wide business, UX, and technical direction. Operates above the per-feature `/design` workflow |
| `product-manager` | Recommends the single next feature to design, based on `strategy.md` and what's already designed/implemented. Advisory only — does not write requirements or code |
| `design-developer` | Feasibility, code reuse, data model/API surface, and ops/scale lens during `analyze.md`; drafts `architecture.md`, revised until `design-security` signs off |
| `design-ui-designer` | Component reuse, visual states, and design-system consistency lens during `analyze.md` |
| `design-ux-designer` | Flow completeness, discoverability, and accessibility lens during `analyze.md` |
| `design-security` | Access control, sensitive data, abuse vectors, and edge/failure-case lens during `analyze.md`; holds sign-off gate on `architecture.md` |
| `design-business` | Business rules, monetization/tiering, compliance, and success-metrics lens during `analyze.md` |
| `design-outside-the-box` | Surfaces unstated assumptions, simpler alternatives, and second-order effects during `analyze.md` |
| `orchestrator` | Breaks a story into the agent contributions it needs and sequences them; coordinates plan/execute/test/commit and routes review findings to specialists during `fix-review` |
| `frontend` | Implements UI/client-side code |
| `backend` | Implements API/server/database code |
| `infrastructure` | Implements Docker, CI/CD, and other infra config |
| `qa` | Writes and runs unit, feature, and end-to-end (Playwright) tests; produces test results |
| `reviewer` | Fresh-context PR reviewer. Receives only the PR diff and `rules/`, no prior conversation. Posts inline comments and a verdict |
| `docs-writer` | Generates technical documentation (per-feature deep dive, changelog, API reference, architecture overview) during `/pr-create` |

A single story is not 1:1 with a single agent — most stories need
contributions from multiple agents (e.g. backend builds an endpoint, frontend
consumes it), sequenced by `orchestrator`.

## Rules

Every agent that writes or tests code must consult, in order:

1. `rules/coding-style.md`
2. `rules/security.md`
3. `rules/testing.md` (specifically the `qa` agent during `test.md`)
4. `DESIGN.md` — for any frontend/UI work (new components, layout changes, styling).
   It's the project's visual design system (color tokens, typography, spacing,
   radii, component specs, do's/don'ts). Consult it before writing or editing any
   HTML/CSS/UI code so new work stays consistent with the established look — don't
   invent colors, spacing, or component styles outside what it defines.

## Agent completion verification

An agent's own report of what it did (success, failure, or silence) is not
sufficient on its own — it can be wrong in either direction: a reported
failure can leave real, usable work on disk, and a reported success (or a
lost/never-received report, e.g. after a background process restart) can
hide that nothing actually happened. Every agent spawn — whether inside a
command's defined workflow or spawned ad hoc — must state, in the prompt,
the concrete artifact that proves completion (a file path with non-stub
content, a non-empty `git diff`, or a passing test command). After the
agent returns, regardless of what it reported, verify that artifact
directly (`ls`/`cat`/`git diff`/run the tests) before treating the task as
done or not-done.

## Git conventions

- One branch per feature: `feature/<feature-folder>` (e.g.
  `feature/LFC-001-user-auth`), created on first `/implement` or
  `/implement-epic` run for that feature if it doesn't exist.
- One commit per story, made only after that story's tests pass. The
  `commit.md` step always shows the proposed commit message and the test
  results, and asks for explicit confirmation before committing — it never
  commits silently.
- Commit message format: `<STORY-CODE>: <short summary>` (e.g.
  `LFC-STORY-001-001: add login form`).
- One PR per feature branch. The PR phase (`pr-create` → `pr-review` →
  `fix-review` loop) runs automatically after a feature's **last** story is
  committed — but `pr-create` still shows the proposed title/body and gets
  confirmation before pushing anything, and re-runs against an existing PR
  update it (push + refresh description) rather than opening a duplicate.
- Review-fix commits made by the `fix-review` loop use the format
  `<feature-folder>: address review (round <N>)`, one commit per cycle,
  pushed only when the full test suite is green.
- No automatic merging, ever — including in headless/scheduled runs. After
  a PR is approved, `implement.md` step 5 asks the user explicitly; only an
  explicit yes merges. Every progress transition (branch created, story
  committed, PR opened/reviewed/merged) is recorded in
  `knowledge/state.json` immediately after it happens.

## On test failure

If `test.md` fails during `/implement` or `/implement-epic`, execution stops
and the failure is surfaced for a decision (fix, skip, or abort) — it is never
auto-retried silently.
